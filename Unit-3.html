Routing & Validation, stop by stop

A request enters your app as a raw URL and leaves as a validated, bound, versioned response. This guide walks that journey in order — how the framework finds the right code to run, how it fills in that code's parameters, and how it checks the data before trusting it.

URL Routing Constraints Model Binding Versioning Validation Action Runs
1Routing

Intro: Routing

Routing is the mechanism ASP.NET Core uses to match an incoming HTTP request (a URL plus an HTTP verb, like GET /products/7) to the piece of code that should handle it — usually a controller action or a minimal API endpoint. Without routing, the framework would have no way of knowing that /products/7 should call GetProduct(int id) instead of some other method.

Routing does three jobs at once:

  • Matching — compares the request's URL and method against a table of known route patterns.
  • Extraction — pulls values out of the URL (like the 7 in /products/7) as route data.
  • Dispatch — hands the request, along with that route data, to the matching endpoint.

In modern ASP.NET Core, routing is registered as middleware in the request pipeline, typically in Program.cs:

Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();

var app = builder.Build();

app.UseRouting();        // locates a matching endpoint
app.UseAuthorization();  // runs after the endpoint is chosen
app.MapControllers();    // registers attribute-routed controllers

app.Run();
Why students should care Every bug that looks like "my controller never gets hit" or "I'm getting a 404 for a route that should exist" traces back to routing. Understanding this stop first makes every later topic — binding, versioning, validation — make sense, because they all depend on the request first being routed correctly.

Example: how the route table picks a match

When several routes could plausibly match a URL, ASP.NET Core picks the most specific one — literal segments beat placeholders, and constrained placeholders beat unconstrained ones:

example
// Route table (registered in this order doesn't matter — specificity wins):
[HttpGet("products/featured")]      // literal segment
public IActionResult GetFeatured() => Ok(_repo.Featured());

[HttpGet("products/{id:int}")]      // constrained placeholder
public IActionResult GetById(int id) => Ok(_repo.Find(id));

// GET /products/featured  -> matches GetFeatured() (literal beats placeholder)
// GET /products/7         -> matches GetById(7)
// GET /products/abc       -> matches NEITHER route -> 404
2Routing

Routing Types: Attribute & Conventional Routing

ASP.NET Core supports two styles of defining routes. You can mix both in the same project, though Web API projects almost always favor attribute routing.

Conventional Routing

Routes are defined once, centrally, using a URL pattern with placeholders. The framework matches any URL that fits the pattern and infers the controller/action from it.

  • Defined centrally in Program.cs
  • Good fit for MVC apps with predictable, uniform URLs
  • Harder to give one action a "special" custom URL

Attribute Routing

Routes are declared directly above the controller or action using [Route], [HttpGet], etc. Each action owns its exact URL.

  • Defined next to the code it routes to
  • Standard choice for Web APIs
  • Full control over each endpoint's URL shape

Conventional routing example

Program.cs
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

This single line matches /Products/Details/7 to ProductsController.Details(int id), because the segments line up: controller = Products, action = Details, id = 7. The ? marks id as optional.

Attribute routing example

ProductsController.cs
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet]                  // GET /api/products
    public IActionResult GetAll() => Ok(_repo.GetAll());

    [HttpGet("{id:int}")]      // GET /api/products/7
    public IActionResult GetById(int id) => Ok(_repo.Find(id));

    [HttpPost]                 // POST /api/products
    public IActionResult Create(Product product) => Ok(_repo.Add(product));
}
Rule of thumb Use conventional routing for classic MVC apps with pages (Home/About/Contact-style URLs). Use attribute routing for Web APIs, where each endpoint's URL and verb need to be explicit and independently controllable.

More conventional routing: multiple patterns

A conventional-routing app can register several patterns, matched top to bottom — handy for giving one area of the site a different URL shape than the rest:

Program.cs
app.MapControllerRoute(
    name: "blog",
    pattern: "blog/{year}/{month}/{slug}",
    defaults: new { controller = "Blog", action = "Post" });

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

// GET /blog/2026/08/routing-in-aspnet   -> BlogController.Post(year, month, slug)
// GET /Products/Details/7               -> falls through to the default route

More attribute routing: token replacement & prefixes

Attribute routing supports tokens like [controller] and [action], so the route text updates automatically if you rename the class — and a controller-level [Route] acts as a shared prefix for every action inside it:

ReviewsController.cs
[ApiController]
[Route("api/[controller]")]           // becomes "api/reviews"
public class ReviewsController : ControllerBase
{
    [HttpGet("{id:int}")]             // GET api/reviews/5
    public IActionResult Get(int id) => Ok();

    [HttpGet("product/{productId:int}")]   // GET api/reviews/product/9
    public IActionResult GetForProduct(int productId) => Ok();

    [HttpGet("~/api/latest-reviews")] // "~/" overrides the prefix entirely
    public IActionResult Latest() => Ok();  // GET api/latest-reviews
}
3Routing

Route Constraints

A route constraint restricts what values a route parameter will accept, so that only URLs matching a certain shape or type reach an action. If the constraint fails, routing simply treats the URL as not matching that route (usually resulting in a 404, or falling through to another matching route).

Constraints are written after the parameter name, separated by a colon: {id:int}.

ConstraintExampleMeaning
int{id:int}Value must parse as an integer
bool{active:bool}Value must be true/false
guid{id:guid}Value must be a valid GUID
alpha{code:alpha}Letters only (a–z, A–Z)
minlength(n){name:minlength(3)}String at least n characters
range(a,b){age:range(18,60)}Integer within a range
regex(pattern){sku:regex(^[A-Z]{3}\d{4}$)}Value must match the regular expression
required{name:required}Segment must be present
OrdersController.cs
// Only matches when id is a real integer, e.g. /api/orders/42
[HttpGet("{id:int}")]
public IActionResult GetOrder(int id) => Ok(_repo.Find(id));

// Combine constraints: int AND within a range
[HttpGet("age/{age:int:range(18,60)}")]
public IActionResult GetByAge(int age) => Ok();

// /api/orders/abc will NOT match the route above — it 404s,
// which is exactly what we want instead of a runtime crash
// trying to convert "abc" to an int.
Common mistake Route constraints are for shaping which URLs match — they are not a substitute for validation. A constraint just filters routing; it doesn't produce friendly error messages or check business rules. That job belongs to Data Annotations or Fluent Validation, further down this line.

More examples: combining and applying constraints

BookingsController.cs
// datetime constraint: only matches a real, parseable date segment
[HttpGet("by-date/{date:datetime}")]
public IActionResult GetByDate(DateTime date) => Ok();
// GET /bookings/by-date/2026-08-06  -> matches
// GET /bookings/by-date/not-a-date  -> 404

// guid constraint: perfect for resource ids that are GUIDs, not ints
[HttpGet("{id:guid}")]
public IActionResult GetById(Guid id) => Ok();

// two placeholders, each with their own constraint
[HttpGet("room/{roomCode:alpha:length(3)}/floor/{floor:int:min(1)}")]
public IActionResult GetRoom(string roomCode, int floor) => Ok();
// GET /bookings/room/SUN/floor/4  -> matches
// GET /bookings/room/S9/floor/4   -> 404 (roomCode fails alpha + length(3))

Example: a custom route constraint

When the built-in constraints aren't enough, you can write your own by implementing IRouteConstraint — useful for rules like "must be a valid product SKU in our system.":

SkuConstraint.cs
public class SkuConstraint : IRouteConstraint
{
    public bool Match(HttpContext? httpContext, IRouter? route, string routeKey,
        RouteValueDictionary values, RouteDirection routeDirection)
    {
        var value = values[routeKey]?.ToString();
        return value != null && Regex.IsMatch(value, @"^[A-Z]{3}\d{4}$");
    }
}

// Program.cs — register it under a friendly name
builder.Services.Configure<RouteOptions>(options =>
    options.ConstraintMap.Add("sku", typeof(SkuConstraint)));

// Usage: [HttpGet("{sku:sku}")]  ->  matches only ABC1234-style codes
4Binding

Model Binding

Once routing has picked the right action, model binding is what fills in that action's parameters from the incoming request. It automatically maps data from route values, the query string, form fields, and the request body into simple types, complex objects, and collections — so you write GetProduct(int id), and never manually parse strings out of the request yourself.

SourceAttributeTypical use
Route data[FromRoute]/products/{id} → id
Query string[FromQuery]?page=2&size=10
Request body[FromBody]JSON payload → a C# object
Form data[FromForm]File uploads, HTML form posts
Headers[FromHeader]Custom headers like X-Api-Key
DI container[FromServices]Inject a service directly into an action
ProductsController.cs
[HttpGet("{id:int}")]
public IActionResult GetProduct(
    [FromRoute] int id,
    [FromQuery] bool includeReviews)
{
    // id comes from the URL segment, includeReviews from ?includeReviews=true
    return Ok(_repo.Find(id, includeReviews));
}

[HttpPost]
public IActionResult Create([FromBody] Product product)
{
    // 'product' is built automatically from the posted JSON body
    _repo.Add(product);
    return CreatedAtAction(nameof(GetProduct), new { id = product.Id }, product);
}
Under the hood When a parameter is a simple type (int, string, bool, Guid), the binder looks in route data and the query string by default. When it's a complex type (a class), the binder assumes the request body by default in API controllers marked [ApiController] — that's why [FromBody] is often optional there, but it's still good practice to be explicit.

Example: binding a complex object from the query string

Model binding isn't limited to simple types — it can build a whole object out of query parameters, which is a common pattern for search/filter endpoints:

ProductsController.cs
public class ProductFilter
{
    public string? Keyword { get; set; }
    public decimal? MinPrice { get; set; }
    public decimal? MaxPrice { get; set; }
    public int Page { get; set; } = 1;
}

[HttpGet("search")]
public IActionResult Search([FromQuery] ProductFilter filter)
{
    return Ok(_repo.Search(filter));
}

// GET /api/products/search?keyword=phone&minPrice=100&maxPrice=500&page=2
// -> filter.Keyword = "phone", filter.MinPrice = 100, filter.Page = 2

Example: binding collections and arrays

example
[HttpGet("by-ids")]
public IActionResult GetMany([FromQuery] int[] ids) =>
    Ok(_repo.FindMany(ids));

// GET /api/products/by-ids?ids=1&ids=2&ids=3
// -> ids = [1, 2, 3]

[HttpPost("bulk")]
public IActionResult CreateMany([FromBody] List<Product> products)
{
    // JSON body: [ { "name": "Mug" }, { "name": "Pen" } ]
    _repo.AddRange(products);
    return Ok(products.Count);
}
5Binding

Bind Attributes

The [Bind] attribute controls exactly which properties of a model are allowed to be set during model binding. It's a safety valve against over-posting (also called mass assignment) — where a malicious or careless client sends extra fields in a request body that end up overwriting properties they shouldn't be able to touch, like IsAdmin or AccountBalance.

UsersController.cs
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public bool IsAdmin { get; set; }   // must NOT be settable by the client
}

[HttpPost]
public IActionResult Register(
    [Bind("Name,Email")] User user)   // only these two are bound
{
    // Even if the client sends { "isAdmin": true } in the JSON body,
    // it is silently ignored — IsAdmin keeps its default value.
    _repo.Add(user);
    return Ok(user);
}

Bind at the parameter vs. the class

[Bind] can also be applied directly on a model class to whitelist properties for every action that binds it, though scoping it per-action (as above) is usually clearer and safer.

Better practice for APIs Most modern Web API code avoids [Bind] altogether by using dedicated DTOs (e.g. RegisterUserDto with only Name and Email) instead of binding the full entity. It achieves the same protection, more explicitly, and keeps your domain models decoupled from your API's request shape.
Common mistake Forgetting that [Bind] only restricts what can be set — it does not validate the values that are set. You still need Data Annotations or Fluent Validation on top of it.

Example: [Bind] applied to the class

User.cs
[Bind("Name,Email,Password")]   // whitelist applies to EVERY action that binds User
public class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public string Password { get; set; }
    public bool IsAdmin { get; set; }
    public decimal AccountBalance { get; set; }
}

Example: [BindNever] and [BindRequired]

Instead of whitelisting on the action, you can blacklist a single property directly on the model — often clearer when only one or two fields need protecting:

User.cs
public class User
{
    public int Id { get; set; }

    [BindRequired]                 // binding fails with ModelState error if missing
    public string Name { get; set; }

    [BindNever]                    // this property can NEVER be set via model binding
    public bool IsAdmin { get; set; }

    [BindNever]
    public decimal AccountBalance { get; set; }
}

// Now every action that binds User is safe automatically —
// no need to repeat [Bind("...")] on each one.

Example: the DTO approach (recommended)

RegisterUserDto.cs
public class RegisterUserDto
{
    public string Name { get; set; }
    public string Email { get; set; }
    public string Password { get; set; }
    // IsAdmin and AccountBalance simply don't exist here — nothing to over-post
}

[HttpPost("register")]
public IActionResult Register(RegisterUserDto dto)
{
    var user = new User { Name = dto.Name, Email = dto.Email };
    _repo.Add(user);
    return Ok(user);
}
6Versioning

Intro: API Versioning

API versioning lets you evolve an API — change response shapes, rename fields, alter behavior — without breaking the clients (mobile apps, other services, third parties) that already depend on the current version. Instead of one endpoint that changes underneath everyone, you publish v1 and v2 side by side, and let each client choose when to move.

In ASP.NET Core, versioning is typically added via the Asp.Versioning.Mvc package (the modern successor to Microsoft.AspNetCore.Mvc.Versioning):

Program.cs
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true; // adds api-supported-versions header
});
Why students should care Versioning is what lets a team ship v2 of an endpoint with breaking changes while v1 keeps working exactly as before for existing clients — it's the difference between "we improved the API" and "we broke production for everyone still on the old version."

Example: one action, two versions

A single controller can expose different behavior per version by mapping the same route to different actions, distinguished by [MapToApiVersion]:

ProductsController.cs
[ApiVersion("1.0")]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/products")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id:int}"), MapToApiVersion("1.0")]
    public IActionResult GetV1(int id) =>
        Ok(new { id, name = _repo.Find(id).Name });          // old, minimal shape

    [HttpGet("{id:int}"), MapToApiVersion("2.0")]
    public IActionResult GetV2(int id) =>
        Ok(_repo.Find(id));                                   // new, full object
}

Example: marking a version as deprecated

ProductsController.cs
[ApiVersion("1.0", Deprecated = true)]   // still works, but flagged to clients
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/products")]
public class ProductsController : ControllerBase { }

// Clients see this in the response headers:
// api-supported-versions: 2.0
// api-deprecated-versions: 1.0
7Versioning

Types of API Versioning

There are four common strategies for telling the server which version a client wants. Each has trade-offs.

1. URL Path Versioning

The version is embedded directly in the URL. Simple, visible, and cache-friendly — the most common approach.

ProductsController.cs
[ApiVersion("1.0")]
[Route("api/v{version:apiVersion}/products")]
public class ProductsController : ControllerBase { }

// GET /api/v1/products
// GET /api/v2/products

2. Query String Versioning

The version is passed as a query parameter, keeping the base URL unchanged.

example
// GET /api/products?api-version=2.0

builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new QueryStringApiVersionReader("api-version");
});

3. Header Versioning

The version travels in a custom HTTP header, keeping URLs completely clean.

example
// GET /api/products
// Header: X-Api-Version: 2.0

builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new HeaderApiVersionReader("X-Api-Version");
});

4. Media Type (Accept Header) Versioning

The version is encoded in the Accept header's media type — the most "correct" from a pure REST standpoint, but the least discoverable for API consumers.

example
// GET /api/products
// Header: Accept: application/json;v=2.0

builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new MediaTypeApiVersionReader("v");
});
StrategyProsCons
URL PathExplicit, easy to test, cache-friendlyVersion baked into every URL / bookmark
Query StringClean base URL, easy to defaultVersion can be dropped or forgotten by clients
HeaderClean URLs, keeps versioning out of the resource pathHarder to test in a browser; less discoverable
Media TypeMost "RESTful"; versions content negotiation itselfLeast intuitive; awkward client tooling

Example: combining strategies with a fallback

It's common to accept a version from more than one source, with a priority order — for example, prefer the header if present, otherwise fall back to the query string:

Program.cs
builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = ApiVersionReader.Combine(
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version"));
});

// A request with BOTH a header and a query string uses the header first.
// GET /api/products?api-version=1.0   Header: X-Api-Version: 2.0  -> resolves to 2.0

Example: calling each style from a client

client examples
// URL Path
GET https://api.shop.com/api/v2/products/7

// Query String
GET https://api.shop.com/api/products/7?api-version=2.0

// Header
GET https://api.shop.com/api/products/7
X-Api-Version: 2.0

// Media Type (Accept header)
GET https://api.shop.com/api/products/7
Accept: application/json;v=2.0
8Validation

Data Annotations

Data Annotations are attributes from System.ComponentModel.DataAnnotations placed directly on model properties to declare validation rules. ASP.NET Core checks them automatically during model binding and populates ModelState with any failures.

AttributePurpose
[Required]Value must be provided (not null / not empty)
[StringLength(n)]Maximum (and optional minimum) string length
[Range(a,b)]Numeric value must fall within a range
[EmailAddress]Value must look like a valid email
[RegularExpression]Value must match a regex pattern
[Compare]Value must match another property (e.g. confirm password)
Product.cs
public class Product
{
    [Required(ErrorMessage = "Product name is required.")]
    [StringLength(100, MinimumLength = 3)]
    public string Name { get; set; }

    [Range(0.01, 100000, ErrorMessage = "Price must be positive.")]
    public decimal Price { get; set; }

    [EmailAddress]
    public string SupplierEmail { get; set; }
}
ProductsController.cs
[HttpPost]
public IActionResult Create(Product product)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState); // returns a 400 with all failed rules

    _repo.Add(product);
    return Ok(product);
}

// Note: controllers marked [ApiController] check ModelState.IsValid
// AUTOMATICALLY before the action even runs, and return 400 for you.
Good to know Data Annotations live on the model itself, so the same rules apply everywhere that model is bound — which is convenient, but also means the model can't easily have different rules for different scenarios (e.g. "required on create, optional on update").

Example: a fuller model with more built-in attributes

RegisterDto.cs
public class RegisterDto
{
    [Required, StringLength(30, MinimumLength = 2)]
    public string Username { get; set; }

    [Required, Phone]
    public string PhoneNumber { get; set; }

    [Url]
    public string? Website { get; set; }

    [CreditCard]
    public string? CardNumber { get; set; }

    [Required, DataType(DataType.Password)]
    [RegularExpression(@"^(?=.*[A-Z])(?=.*\d).{8,}$",
        ErrorMessage = "Password needs 8+ chars, one uppercase letter, one digit.")]
    public string Password { get; set; }

    [Compare(nameof(Password), ErrorMessage = "Passwords do not match.")]
    public string ConfirmPassword { get; set; }
}

Example: writing a custom Data Annotation

When the built-in attributes aren't enough, implement ValidationAttribute to create your own reusable rule:

FutureDateAttribute.cs
public class FutureDateAttribute : ValidationAttribute
{
    protected override ValidationResult? IsValid(object? value, ValidationContext context)
    {
        if (value is DateTime date && date <= DateTime.Today)
            return new ValidationResult("Date must be in the future.");

        return ValidationResult.Success;
    }
}

// Usage on a model:
public class Booking
{
    [FutureDate]
    public DateTime CheckInDate { get; set; }
}
9Validation

Intro: Fluent API Validations

FluentValidation is a popular open-source library that moves validation rules out of the model and into dedicated validator classes, written using a fluent, chainable C# syntax. Instead of decorating properties with attributes, you describe rules in code — which makes complex, conditional, or reusable validation logic far easier to express and test.

ProductValidator.cs
public class ProductValidator : AbstractValidator<Product>
{
    public ProductValidator()
    {
        RuleFor(p => p.Name)
            .NotEmpty().WithMessage("Product name is required.")
            .Length(3, 100);

        RuleFor(p => p.Price)
            .GreaterThan(0).WithMessage("Price must be positive.");

        RuleFor(p => p.SupplierEmail)
            .EmailAddress()
            .When(p => !string.IsNullOrEmpty(p.SupplierEmail));
    }
}
Program.cs
builder.Services.AddValidatorsFromAssemblyContaining<ProductValidator>();
builder.Services.AddFluentValidationAutoValidation();

Once registered, FluentValidation plugs into the same model-validation pipeline as Data Annotations — a client posting an invalid Product still gets a 400 response with clear error messages, but the rules themselves now live in ProductValidator, completely separate from the Product class.

Example: running a validator manually (outside MVC)

Because a validator is just a plain class, you can call it directly — in a console app, a background job, or a unit test — with no controller or HTTP pipeline involved at all:

Program.cs (console)
var validator = new ProductValidator();
var product = new Product { Name = "Mu", Price = -5 };

ValidationResult result = validator.Validate(product);

if (!result.IsValid)
{
    foreach (var failure in result.Errors)
        Console.WriteLine($"{failure.PropertyName}: {failure.ErrorMessage}");
}
// Output:
// Name: The length of 'Name' must be at least 3 characters.
// Price: 'Price' must be greater than '0'.

Example: unit testing a validator

ProductValidatorTests.cs
public class ProductValidatorTests
{
    private readonly ProductValidator _validator = new();

    [Fact]
    public void Fails_when_name_is_too_short()
    {
        var result = _validator.TestValidate(new Product { Name = "Mu", Price = 10 });
        result.ShouldHaveValidationErrorFor(p => p.Name);
    }

    [Fact]
    public void Passes_for_a_valid_product()
    {
        var result = _validator.TestValidate(new Product { Name = "Mug", Price = 10 });
        result.ShouldNotHaveAnyValidationErrors();
    }
}
10Validation

Fluent API Validation Types

FluentValidation ships a rich set of built-in validators, all chained onto RuleFor.

ValidatorChecks
NotEmpty()Not null, not empty string, not default value
NotNull()Value is not null
Length(min, max)String length falls within a range
EmailAddress()Value is a syntactically valid email
Matches(regex)String matches a regular expression
GreaterThan() / LessThan()Numeric/date comparisons
InclusiveBetween(a, b)Value falls within an inclusive range
Must(predicate)Custom logic — any condition you can express as a function
When() / Unless()Applies a rule only under a given condition
SetValidator()Delegates to another validator for a nested/child object
OrderValidator.cs
public class OrderValidator : AbstractValidator<Order>
{
    public OrderValidator()
    {
        RuleFor(o => o.Quantity)
            .InclusiveBetween(1, 100);

        RuleFor(o => o.Sku)
            .Matches(@"^[A-Z]{3}\d{4}$")
            .WithMessage("SKU must look like ABC1234.");

        RuleFor(o => o.DeliveryDate)
            .GreaterThan(DateTime.Today)
            .When(o => o.IsExpressDelivery);

        RuleFor(o => o.Customer)
            .SetValidator(new CustomerValidator());   // nested object

        RuleFor(o => o)
            .Must(o => o.Total == o.Quantity * o.UnitPrice)
            .WithMessage("Total does not match quantity × unit price.");
    }
}
RuleFor() RuleForEach() When() / Unless() Must() WithMessage() SetValidator()

Example: validating a collection with RuleForEach

CartValidator.cs
public class CartValidator : AbstractValidator<Cart>
{
    public CartValidator()
    {
        RuleFor(c => c.Items).NotEmpty().WithMessage("Cart cannot be empty.");

        RuleForEach(c => c.Items).ChildRules(item =>
        {
            item.RuleFor(i => i.Quantity).GreaterThan(0);
            item.RuleFor(i => i.ProductId).NotEmpty();
        });
    }
}
// Every item in c.Items is validated individually — errors report
// which index in the collection failed, e.g. "Items[2].Quantity".

Example: a fully custom validator with Must()

RegisterValidator.cs
public class RegisterValidator : AbstractValidator<RegisterDto>
{
    private readonly IUserRepository _users;

    public RegisterValidator(IUserRepository users)
    {
        _users = users;

        RuleFor(r => r.Email)
            .NotEmpty()
            .EmailAddress()
            .MustAsync(async (email, cancellation) =>
                !await _users.EmailExistsAsync(email))
            .WithMessage("An account with this email already exists.");

        RuleFor(r => r.Password)
            .MinimumLength(8)
            .Must(p => p.Any(char.IsDigit))
            .WithMessage("Password must contain at least one digit.");
    }
}
// Shows validation reaching into a database (MustAsync) —
// something Data Annotations cannot do at all.
11Validation

Advantages of Fluent Validation

Compared to Data Annotations, FluentValidation trades a little extra setup for a lot more flexibility:

  • Separation of concerns — validation logic lives outside the model, so the model stays a plain data class with no framework-specific attributes cluttering it.
  • Testability — a validator is just a class; you can unit test it directly by calling Validate(), without spinning up MVC or ModelState at all.
  • Complex & conditional rules — When(), Unless(), and Must() express rules that would be awkward or impossible with attributes alone, like "delivery date is required only for express orders."
  • Reusable, composable validators — one validator can call another via SetValidator() for nested objects, and validators can be reused across DTOs that share shape.
  • Multiple validators per type — you can define a "create" validator and a separate "update" validator for the same model, something attributes on the model can't express.
  • Cleaner error messages — messages are defined alongside logic in fluent, readable chains, and can reference other properties or computed context easily.

Choose Data Annotations when…

  • Rules are simple and apply everywhere the model is used
  • You want validation visible at a glance on the model itself
  • The project is small and doesn't need much conditional logic

Choose Fluent Validation when…

  • Rules are complex, conditional, or differ by scenario
  • You want validators to be independently unit-testable
  • Models are shared across layers and shouldn't carry validation attributes
Takeaway for the course Data Annotations are the fast, built-in default — great for learning and for straightforward models. FluentValidation is what most production teams reach for once validation logic grows past what a handful of attributes can cleanly express.

Example: the problem Data Annotations can't solve

Imagine a Product where Sku is required on create but read-only (and irrelevant to validate) on update. One model, one set of attributes, can't express two different rule sets:

the problem
public class Product
{
    [Required]     // always required — even during an update where it's not sent
    public string Sku { get; set; }
}

Example: FluentValidation's fix — separate validators per scenario

the fix
public class CreateProductValidator : AbstractValidator<Product>
{
    public CreateProductValidator()
    {
        RuleFor(p => p.Sku).NotEmpty();      // required only when creating
        RuleFor(p => p.Name).NotEmpty();
    }
}

public class UpdateProductValidator : AbstractValidator<Product>
{
    public UpdateProductValidator()
    {
        RuleFor(p => p.Name).NotEmpty();     // Sku isn't validated here at all
    }
}

// The controller resolves whichever validator fits the action being called:
[HttpPost]
public IActionResult Create(Product product, [FromServices] CreateProductValidator v)
{
    var result = v.Validate(product);
    return result.IsValid ? Ok(product) : BadRequest(result.Errors);
}
